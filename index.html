01
Foundation

The Philosophy

why does a garbage collector exist. seriously. think about it. programs create the same things, destroy them, then create them again. the GC is just cleaning up a mess that shouldnt exist in the first place. its a janitor for a problem you caused yourself.

so i thought — what if you just NEVER throw it away. pool everything. every calculation, every result, every state gets an index. next time you need it, return the index. done. no recompute. no reallocate. no collect. ever.

thats it. thats the whole thing. everything else in this doc is just that one idea applied everywhere.

PELTGC isnt a memory optimization. its not a GC replacement. its a different way of thinking about computation entirely. the pool isnt a feature you turn on. its the foundation everything runs on.

Pooling is the GC. PELT-GC. the garbage collection technique where the technique is — never garbage collect.

What ART and Lazy Mean

ART — At Runtime. smarter than JIT. JIT only compiles when it sees something for the first time at runtime. ART does two things — it prebakes at the start from reading the scripts, AND compiles at runtime for anything it missed. so almost nothing is ever cold. JIT is reactive. ART is proactive AND reactive.

Lazy — the slot exists, the index is assigned, but the value isnt there yet. the queue already saw it coming and reserved the spot. when it arrives — slot is waiting. just fill and go.

Merged — multiple pointers collapsed to one entry. chapter 05.

How Indices Get Assigned

sequential. first calculation the pool sees is [1]. second is [2]. the queue pre-reserves indices for calculations it already knows are coming — so lazy entries have their index before they arrive. the pool never renumbers. an index is permanent for the session. always.

Memory Regions and Deactivation

under pressure, cold regions deactivate. they stop using active memory but keep their index. when needed again — instant reactivation. nothing lost. it just sleeps.

this is NOT eviction. eviction destroys the result, forces recompute. deactivation just pauses it. huge difference. the pool never forgets. it only sleeps.

this is the basic version. the pool is actually more advanced than this — regions observe each other, compare, merge the best parts of both. next chapter.

Pool Evolution — Genetic Selection

pools dont just sit there. they evolve. two pool regions doing almost the same thing — the system notices. it takes the best parts of both and collapses them into one entry that outperforms either. the weak version dies. the better version survives. automatically. no dev involvement.

you know evolution games where the AI passes the best genes to the next generation. the weak dies, the strong survives, the next gen is better. thats literally what pools do here.

its not just an analogy

GENES
Pool entry characteristics — hit rate, precision level, tier placement, routing speed, digit trimming threshold, nudge range. These are the traits that determine which entry is stronger.
entry traits
SELECTION
Runtime usage is selection pressure. Entries that get hit more survive. Entries that go unused weaken and die. The pool doesn't decide what matters — reality does, through repeated use.
natural selection
CROSSOVER
Two near-identical pool entries with overlapping function collapse into one. The surviving entry inherits the best hit rate, the tightest precision threshold, the most efficient routing path from both parents.
merge best traits
MUTATION
Digit trimming and nudging slightly adjust values to find better matches. These micro-adjustments are mutations — small harmless changes that discover more efficient pool configurations over time.
micro-adjustment

what this does to RAM

someone said the pool would fill 32GB with unique states. no. because the pool isnt accumulating — its condensing. near-identical entries merge. weak entries die. redundancy collapses. it converges toward the smallest possible representation of what the game actually needs. it gets smaller AND better at the same time. no other caching system does that.

Traditional cache — only grows

Session 10: 10,000 entries
Session 100: bloated, evicted, restarted
Always grows. Never improves.
PELTGC pool — evolves and condenses

Smaller. Faster. More accurate. Always.

propagation up the hierarchy

best session pool entries get promoted to the game pool. best game pool entries propagate up to the OS pool. one insight from one session can eventually become a universal constant shared across every app on the machine. good calculations rise. thats it.

session 100 has a smaller pool than session 10. not a bigger one. because everything that was the same thing got collapsed. everything useless died. what remains is exactly what matters. nothing else.

Digit Trimming — The Self-Calibrating Threshold

two values that look different might be the same thing. how does the pool figure that out? not with a manually configured threshold — thats stupid, every domain needs a different one. instead: digit trimming. keep removing trailing digits from both values until they hit a match that already exists in the pool.

If someone asks what 2.0000001 and 2.0000002 are, they are both just 2. The pool figures that out by itself.
Traditional — manual threshold
define threshold = 0.001
if abs(a - b) < threshold: match
Wrong context = wrong threshold
Requires developer configuration
PELTGC — digit trimming
25626221590 vs 25626222590
trim → 256262215 | 256262225 — no match
trim → 25626221 | 25626222 — no match
trim → 2562622 | 2562622 — MATCH

no context needed. no config. no domain knowledge. trim until the pool confirms a match. the pool defines its own threshold by what it already contains. self-calibrating. zero dev input. ever.

nudging

sometimes you dont even need to trim. if two values are close enough, the pool tries nudging the incoming value up AND down — whichever direction hits an existing entry with the smallest perceivable change. if neither direction changes anything you'd notice — nudge happens, values collapse to one. done.

Traditional — strict equality
1.00001 → stored as entry A
1.00002 → no match found
1.00002 → stored as entry B
Two entries. Imperceptible difference.
PELTGC — bidirectional nudge
1.00001 → stored as entry A
1.00002 → try +0.00001 → 1.00003 — no match
1.00002 → try -0.00001 → 1.00001 — match A
nudge down → matches entry A. One entry.

trimming reduces precision to find a match. nudging steps in either direction to find a match. same goal — collapse what you cant perceive into what you already know. threshold is always human perception. not math. not config. humans.

Merged Pointers — Bytecode Deduplication

two bytecode instructions doing the exact same thing with the same linking? thats not two instructions. thats one instruction written twice. PELTGC deletes the copy. both call sites point to the surviving one. bytecode shrinks. nothing is lost.

two identical sentences in a book dont need printing twice. print once. reference twice. same meaning. half the space.

same function. same linking. one entry.

compiler scans all bytecode before execution. finds two instructions — identical signature, identical inputs, identical dependencies. deletes one. redirects everything to the survivor. the duplicate never runs. at runtime it never existed.

Normal — duplicate bytecode
fn_gravity_apply(mass, vel) → addr 0x3F00
fn_gravity_apply(mass, vel) → addr 0x4A10
Both execute. Both cost. Both exist.
4 pointers → 4 addresses → 4 pool entries
PELTGC — merged bytecode
fn_gravity_apply(mass, vel) → addr 0x3F00 [kept]
fn_gravity_apply(mass, vel) → deleted
All callers → redirected to [13]
4 pointers → 1 address → 1 pool entry

speed bonus

when multiple call sites share one pool entry — that entry accumulates hits faster. crosses tier thresholds sooner. gets promoted to cache earlier. merging doesnt just reduce count. it accelerates learning by concentrating usage.

Normal — 4 separate bytecode entries
ptr_A→0x3F00
ptr_B→0x4A10
ptr_C→0x5C20
ptr_D→0x6D30
PELTGC — 1 entry, 4 references
A, B, C, D→[13]
Identical function. Identical linking. One pool entry. Pointer table stays tiny. Fits in cache. All 4 cost same as 1.

Physics Tiers — Self Optimizing

not all calculations are equal. and the prebake isnt blind — it reads the actual game scripts before launch and figures out what will actually be needed.

script-aware prebaking

compiler reads every script before launch. identifies which math functions are actually used — sin, cos, tan, coordinates, physics constants, whatever. simple game with no arcs doesnt need trig prebaked. flight sim needs all of it. the prebake is tailored to what the game actually does. not a generic assumption about what games need. your game. your scripts.

Traditional — generic prebake
Load gravity — always
Load sin/cos/tan — always
Load collision matrices — always
Simple game pays full cost of complex engine
PELTGC — script-read prebake
Read scripts → gravity used? Prebake it.
Read scripts → sin/cos used? Prebake them.
Read scripts → no trig? Don't touch it.
Every game pays only for what it needs.

intent-based pooling

the compiler doesnt just look for exact repeated calculations. it looks for intent. 4*4+1.5-1.005 appears once — does it appear anywhere else? does any other script intend to produce the same result a different way? if yes — pooled immediately. before it even runs.

theoretically, everything can be prepooled. compiler read the entire game. it knows every calculation that will ever be asked for. it pre-answers them all. first frame could launch fully warm.

Everything can theoretically be prepooled. The compiler has the entire script. The script contains every calculation the game will ever need. Given enough prebake time, a game could launch with its entire pool already warm — first frame at full speed, cold start eliminated entirely.

COMMON
Pre-baked at startup from script analysis. Gravity, standard collisions, any math function the compiler found in the scripts. Always ready. Zero compute. Ever. Known before the first frame runs.
instant
RARE
Calculations the compiler found but couldn't fully prebake — context-dependent results, values that depend on player state. Computed once when first encountered at runtime. Stored immediately.

Demotion

the pool isnt a flat list. its a living priority structure tuned to this game, this machine, this player, right now. different for every session. always correct.

The Pool Learns

Pool Hierarchy

pools arent isolated. they form a hierarchy. before checking its own pool, a game checks the OS pool. gravity, standard math, universal physics — computed once across the whole machine. not once per game. once. period.

OS POOL
Universal calculations. Gravity, basic math, standard physics. Shared across all running applications. Read-only to games — nothing can corrupt it. More PELTGC applications running = everyone benefits.
read-only
GAME POOL
Game-specific calculations. Physics unique to this title, asset-specific vertices, game logic. Writable by the game, invisible to other games. Falls back to OS pool before computing anything new.
isolated write
SESSION POOL
Player-specific patterns from this run. Learned automatically. Cleared between sessions or persisted to disk. The most personal layer — tuned to exactly how this player plays on this machine.
personal

Machine Uniqueness

every pool is a fingerprint of the machine that built it. floating point behavior, hardware timing, truncation — all different at the silicon level. a pool optimized for one CPU means nothing on another. the machine is the pool. inseparable. transferring pools isnt a security hole — its physically nonsensical.

Session Persistence

session pool can persist to disk. next launch — personal pool loads before frame one. system already knows how you play before you press anything. cold start effectively gone after session 1. everything it learned is just waiting.

opt-in per game. competitive games might want a fresh pool every run — player behavior is supposed to be unpredictable. open world games benefit massively from persistence — same areas, same physics, hundreds of hours.

Fallback Behavior

no OS pool support? game pool takes over. gravity pools in the game pool instead. nothing breaks. hierarchy collapses to flat game pool. slightly less efficient than full PELTGC hardware — but still dramatically better than any traditional engine. the game pool is still running.

each core owns its slice — but what if core 3 needs something core 0 already computed? it doesnt recompute. it checks the shared index table — lightweight read-only map of where every index lives. result is in core 0's memory. core 3 reads it. no duplication. no transfer. pointer across the boundary. done.

read-only by design. no core writes to another core's pool. index table is append-only. reads are free. contention is physically impossible.

Fractional Routing — Half-Pooled Solutions

legacy systems have an all-or-nothing problem. dont have the exact final answer? recalculate the entire thing from scratch. every time. the equation is a locked black box.

PELTGC doesnt see a black box. it sees lego blocks.

When you solve a math problem, you don't always start from zero. You recognize the tricks. You look at the intermediate steps, realize you've done half of it before, and jump to the end. The hardware should do the exact same thing.

compound intent resolution

novel calculation — player jumping out of a moving vehicle into a windstorm. final combination is new. individual forces are not. break it down. route what you know. only compute whats actually new.

Legacy CPU — All or Nothing
1. Calculate Gravity: 9.81 * Mass
2. Calculate Wind: 1.2 * Velocity
3. Add them together for Total Force
3 heavy ALU operations. Complete waste of time.
PELTGC — Fractional Routing
1. Gravity = [Index 14] (Routed instantly)
2. Wind = [Index 42] (Routed instantly)
3. Add [14] + [42] -> Pool as [Index 43]
1 light addition. Cold Starts are almost never 100% cold.

a "new" calculation is rarely new. its a novel arrangement of already-pooled pieces. compiler finds the half-pooled solutions and skips over the math it already knows. execution never starts from zero.

This flattens the Cold Start curve. The more you play, the more "puzzle pieces" the pool collects. Even if the game generates a procedural, never-before-seen event, PELTGC solves it almost instantly by snapping together the pooled fragments of past events.

Rendering

NDF — No Duplicate Frames

NDF doesnt check if objects moved. it checks if the screen itself changed. the pixel is the atomic unit. triangles, vertices, lighting — inputs that feed into the pixel. the pixel chunk is the final verdict.

The GPU's job is to produce pixels. If the pixels haven't changed, the GPU has no job. NDF makes that determination before the GPU is ever asked.

The 4×4 Grid

every frame splits into a 4×4 grid of pixel regions. each region evaluated independently. four checks per chunk:

HUE
Did the color tone of this region shift? A sunset changing from orange to red triggers this. A static wall does not. Digit trimming collapses imperceptible hue shifts to the same value automatically.
color tone
BRIGHTNESS
Did the lighting on this region change? A torch flickering, a shadow moving, a day/night cycle advancing — all brightness checks. Static indoor lighting never triggers this.
lighting
COLOR DATA
Full RGB value check. The complete color fingerprint of the region. If hue and brightness passed but a texture detail changed — this catches it. The most precise of the four checks.
full RGB
GEOMETRY
Did any triangle or vertex that projects into this region move? A vertex moving in world space only matters if its projection falls inside this chunk. Movement outside the chunk is invisible to it.
projection

all four checks per chunk. all unchanged — held from previous frame. zero GPU cost. any one changes — only that chunk redraws. not the whole frame. not the whole object. just the chunks that changed.

Why Pixels Are the Foundation

triangles and vertices dont directly decide if a frame rerenders. they feed into the pixel check. a tree's vertices moving only matters if they project into a chunk where hue, brightness, or color also crossed the digit trimming threshold. imperceptible in the final pixel — NDF treats it as identical.

NDF's bar for "identical" is human perception. not math. if you cant see it, it didnt change. simple.

Traditional — object-based decisions
Object moved? Re-render entire frame.
Light changed? Re-render everything lit.
Particle effect? Full pass every frame.
GPU workload = scene complexity
PELTGC NDF — chunk-based decisions
Check 4×4 chunks: hue, brightness, color, geometry
3 chunks changed? Redraw 3 chunks only.
Particle effect off-screen? Zero chunks changed.
GPU workload = what visually changed on screen

queue tells NDF whats coming before the frame is due. no scripts touching visible objects — skip chunk checks entirely, answer already known. scripts affecting specific regions — pre-mark those chunks, ignore the rest. not reactive. targeted before it begins.

GPU workload becomes proportional to visible change — not to scene complexity, not to frame rate, not to polygon count. A menu screen with no movement costs 0% GPU. A cutscene with a slow camera pan costs almost nothing. Active combat costs exactly as much as the number of screen chunks that actually changed. Nothing more. Ever.

NDF was not a design target. It emerged naturally from the pool architecture. Once pixel chunks are the atomic rendering unit and the queue sees what is coming before it arrives, skipping unchanged regions becomes the automatic default — not an optimization pass. The feature aimed itself at the correct level of granularity.

Hexagon Pixels — The Perfect Grid

square pixels are from the 1950s. theyre physically wrong — corner distance is longer than side distance. jagged edges everywhere. to hide it, modern hardware burns enormous compute on anti-aliasing. blurring edges to fake what the geometry cant deliver.

hexagons are equidistant. every neighbor exactly the same distance from center. natural curves. the human retina is literally made of hexagonal photoreceptors. not squares. hexagons. so why do we use squares?

The industry uses squares because the math for hexagons is too heavy to calculate 60 times a second. PELTGC only calculates it once.

Perfect clarity. Zero ongoing compute.

NDF Synergy

TAA and modern AA techniques ruin static frames. they jitter the camera every single frame to gather sub-pixel data — meaning the frame is always changing even when nothing moves. breaks traditional caching. breaks NDF.

hex pixels eliminate AA entirely. no jitter needed. frame stays mathematically identical. NDF works perfectly. static hex scene — 0.0% GPU. not close to zero. exactly zero.

hex displays were always the dream. bottlenecked by the processor's inability to do the math fast enough. PELTGC routes the math instead of computing it. the perfect display finally has the architecture to drive it.

GPU Architecture — The Real Target

the GPU arms race is just spending money on a philosophy problem. every generation — more cores to run the same duplicate calculations faster. more VRAM for the same redundant data. more power to push the same unchanged frames at higher resolution.

the bottleneck was never hardware. it was always: why are we doing this work twice.

PELTGC at the GPU level means the silicon itself has the pool baked in. not software telling the GPU to cache things — hardware that natively understands pool indices. shader ran last frame with identical inputs — doesnt execute. returns the pooled result. instantly.

What Changes at Silicon Level

traditional GPU core: fetch → decode → ALU → write. every operation. every time. no exceptions.

PELTGC GPU core adds pool lookup before fetch. hit — fetch, decode, ALU never wake up. result returned directly. ALU idles. power near zero. miss — normal pipeline, pool result on the way out.

Traditional GPU core — always executes

Same shader inputs as last frame?
Doesn't matter. Runs anyway.
Full power every cycle regardless
PELTGC GPU core — pool first
Pool check → hit → return result
Fetch, Decode, ALU never wake up
Core draws near-zero power
Miss → normal pipeline + pool on exit

Duplicate draw calls — hardware-level deduplication. Identical vertices — one calculation shared across every core that needs it. Unchanged pixels — the silicon skips them without NDF telling it to. The GPU stops being a calculator that forgets everything between frames.

less power. less heat. less silicon. more performance. doesnt make expensive hardware faster. makes cheap hardware capable. the kid whos lagging — stops lagging. serves every price point. not just the top.

The Interrogation — Addressing the Skeptics

When you propose a system that eliminates the garbage collector and bypasses traditional CPU logic, computer science veterans will ask the same four questions. Here are the answers.

Q: Searching RAM takes 100+ cycles. Basic math takes 1 cycle. If you search a pool instead of calculating, aren't you making it slower?

A: It doesn't search. It routes.

Traditional memoization creates a hash, searches a massive dictionary, and asks, "Have I done this?" That is slow. PELTGC uses a Pre-Compiled Ledger. The compiler already knows the intent before the instruction fires. It acts as a hardware-level switch.

If someone asks you what 1+1 is, you don't hold up your fingers and count. You just say 2.

When the system sees a calculation it knows, it does not wake up the ALU. It does not open or close logic gates. It simply follows a hardcoded redirect pointer to the answer. O(1) execution. Zero search time. Zero compute time.

The Restaurant Analogy: A normal CPU is a chef who cooks every burger from scratch, even if 10 are ordered. A memoized CPU searches the massive kitchen to see if a burger is already made (which takes too long). PELTGC is just a numbered menu. The waiter asks for #42, and #42 is handed over instantly.

Q: If Thread 2 needs the result of Thread 1, Thread 2 has to stop and wait. How does PELTGC avoid thread lock?

A: Threads don't have egos. They serve the queue.

In a legacy system, threads are rigidly assigned to tasks. If Thread B needs Task A to finish, it goes to sleep and burns cycles waiting (Thread Lock). In PELTGC, the Script Queue knows the entire dependency graph.

Legacy CPUs
Thread 1: Cutting Brick A
Thread 2: Needs Brick A. Waiting... (wasted cycles)
PELTGC Threads
Thread 1: Cutting Brick A
Thread 2: Becomes Calc_A. Helps cut Brick A.

The moment a thread hits a dependency wall, it seamlessly shifts roles and helps process the exact bottleneck it was waiting on. No mutexes. No wait states. Just continuous forward momentum.

Q: RAM is physical. If you never delete anything, won't the 32GB pool eventually hit 100% and crash?

A: Resident Dormancy and Zero-Cost Overwriting.

Other engines move "cold" memory to a slow SSD (Pagefile), causing massive lag. Or they freeze the game to sweep and delete it (Garbage Collection). PELTGC does neither.

When data gets cold, it goes dormant. It stays in physical RAM but draws zero active processing overhead. If the physical RAM actually hits 99.9% capacity, the hardware natively tracks cache hits. It silently allows the newest calculations to overwrite the absolute coldest, most forgotten indices. The pool doesn't crash; it organically replaces its oldest memories without ever stopping the execution pipeline.

Q: How does NDF (No Duplicate Frames) know a frame is identical without asking the GPU to render it first?

A: The frame is just an equation.

PELTGC treats the entire scene state as a mathematical formula of pool indices. If the inputs have not changed, it is a mathematical certainty that the output will not change.

FRAME HASH
Frame 1: [Cam_Pos_7] + [Light_State_12] + [Player_Anim_4] = Output_A
Frame 2: [Cam_Pos_7] + [Light_State_12] + [Player_Anim_4] = Output_A (Skip GPU)

The hardware checks the ledger. Camera moved? No. Lighting changed? No. Player moved? No. The GPU is completely bypassed. The display controller simply holds the previous buffer. The GPU drops to 0% utilization while delivering perfect visual continuity.

Ten More Questions — All Solved

These are the questions that come after the first four. The ones that only appear once someone has understood the system well enough to push deeper. Every single one has an answer built into the architecture.

Q: Floating point values have billions of possible states. How can the pool ever match them?

A: Digit trimming. The pool matches itself.

The pool does not need a manually configured threshold. It keeps removing trailing digits from both values until they converge on a key that already exists. 2.0000001 and 2.0000002 both trim to 2. The pool defines the precision level by what it already contains. No configuration. No context needed. Self-calibrating by design.

Q: What if two scripts produce contradicting certain outcomes simultaneously? Player dies AND player heals at the same moment?

A: The queue reads both scripts and compares values.

If the heal value is lower than the damage value — death is certain. Pre-load death. If the heal value is higher — survival is certain. Pre-load survival. The queue does not guess between them. It reads both scripts, compares the numbers, and the math decides. One outcome. Always certain.

CONFLICT RESOLUTION
damage: 80 heal: 30 → net: -50 → pre-load death
damage: 80 heal: 120 → net: +40 → pre-load survival

Q: If a script reads pool state to determine its outcome, and the pool pre-loads based on that script — isn't that circular?

A: The queue reads the script. That's all it needs.

If the result is already in the pool, the script doesn't need to run at all — the pool already has the answer. The queue only reads scripts for outcomes that aren't pooled yet. Once something is pooled, the script is bypassed entirely. There is no loop because the pool eliminates the condition that would create one.

Q: The intentional delay sounds bad. Won't players feel it?

A: The delay adapts based on cache hits.

The queue monitors cache hit rate in real time. High cache hits means the pool is warm and pre-loading fast — delay shrinks. Low cache hits means the pool needs more time to prepare — delay grows slightly. The system calibrates its own breathing room based on how much it actually needs. In a warm session the delay is effectively zero. The player never feels what they never notice.

Q: In multiplayer, two machines have different pools and different queue timings. How does this not desync?

A: Partial sync. Input is queued. Everything else follows the server.

Player input enters the client queue and is transmitted to the server. The server's queue reads the scripts that input triggers and pre-loads outcomes. Both sides resolve to the same result because the server is canonical truth and the pool is deterministic. The client queue handles input. The server queue handles world state. They coordinate without being identical.

Q: What about completely procedurally generated games? The pool has never seen any of it.

A: Fractional routing. Cold starts are almost never 100% cold.

A procedurally generated event is novel as a combination — but its sub-pieces are not. Gravity is gravity. Wind is wind. Collision physics is collision physics. PELTGC routes every sub-component it already knows and only computes the genuinely new combination at the top. The more the pool has seen, the smaller the cold piece becomes. Even in a fully procedural game, the pool is solving most of the work from day one.

Q: Thread collisions seem inevitable at scale. Twelve threads will eventually want the same thing.

A: They never reach that point. The queue separates them before they start.

Every thread's job is queued before execution begins. The queue sees what every thread is about to do and distributes work so no two threads are ever reaching for the same calculation. A collision requires two threads to want the same thing at the same time. The queue makes that structurally impossible by the time threads are running.

Q: How does the pool decide what to keep vs what to let go dormant under memory pressure?

A: Efficiency tracking. The pool knows exactly what is worth keeping.

Every entry tracks cache hits and compute matches — how many times it was used and how much compute it saved. Low efficiency entries merge with similar ones or lose their detail and keep only the useful core. The pool curates itself continuously. It never bloats blindly. It gets leaner and smarter over time, not just larger.

Q: Cold start sounds rough for the first session. How warm is it really on first run?

A: Warmer than it sounds. The queue is active from frame one.

Even on first run the Script Queue is reading scripts and pre-loading certain outcomes within the same session as they become known. The pool fills live as the game runs. By the middle of the first session it is already routing large portions of work. Cold start is not a blank session — it is a live calibration that gets warmer every minute.

Q: NDF seems reactive — it checks after the fact whether a frame changed. Can it do better?

A: It already does. The queue tells it before the frame is due.

If no scripts touching scene state are in the queue, NDF knows with certainty the next frame will be identical — before the frame cycle even begins. The GPU skip is preventive, not reactive. NDF does not check after the fact. It reads what is coming and acts before it arrives.

Every question above has an answer that was already inside the system. The architecture is not defended by adding exceptions. It is defended by showing the design already thought further ahead than the question did.

Hot entries that the system learned are used constantly. Promoted specifically because their hit rate justifies permanent cache residency. They live in L3 cache — still orders of magnitude faster than RAM.
L3 cache
RARE
Cold and dormant entries. These live in RAM. They are not routed frequently — if they were, they would be promoted. The 100-300 cycle cost applies here, but these entries are cold by definition. They are rarely touched.
RAM — rarely hit

The critique assumes every pool lookup goes to RAM. That is only true for entries the system has correctly identified as rarely used. Everything hot is in cache. Everything truly constant is on-die. The architecture self-organizes exactly the way the critique demands — it just does it automatically through the tier system rather than manually.

A 1-cycle ALU operation beats a 300-cycle RAM lookup. A 1-cycle ALU operation does not beat a 4-cycle L1 cache lookup. PELTGC does not compete with the ALU on RAM lookups. It competes with the ALU on cache lookups — and it wins on every calculation it has seen before.

Attack 2: The Causality Paradox. You cannot skip addresses 1 and 2 to reach address 3 without knowing what 1 and 2 produce as inputs first. You need the past to find the future.

The merge happens at known outputs, not by skipping unknown inputs.

The critique reads chain compression as: skip addresses 1 and 2, jump to 3. That is not what happens. What actually happens:

What the critique thinks happens
addr 1: player velocity — SKIPPED???
addr 2: wind force — SKIPPED???
addr 3: combined force — pool hit
Problem: how do you get addr 3's key without 1 and 2?
What actually happens
addr 1: player velocity — pool hit [route, ~4 cycles]
addr 2: wind force — pool hit [route, ~4 cycles]
addr 3: combined force — pool hit [route, ~4 cycles]
All three routed. Total: ~12 cycles. Not skipped — fast.

Addresses 1 and 2 are not skipped. They are routed — meaning they execute at cache speed instead of compute speed. Their outputs are known immediately. Those outputs form the key for address 3. Address 3 is then also routed. The chain is not shortcut by skipping steps — it is compressed by making every step instant. The causality is preserved. The compute is eliminated.

The merge in Chapter 4 refers to pointer deduplication — collapsing multiple pointers that reference the same already-computed result into one. Not to skipping prerequisite steps.

Attack 3: State Space Explosion. Even trimmed to 2 decimal places, an open world game produces trillions of unique states. The index map alone fills 32GB.

The pool is not an exhaustive state map. It is a curated efficiency structure.

The critique imagines the pool stores every unique combination of X, Y, Z, rotation, velocity, and animation frame ever encountered. That would indeed be trillions of entries. That is not what the pool stores.

The pool stores individual calculation results — not combined world states. Gravity at 9.81 is one entry. A velocity of 5.2 m/s is one entry. The result of multiplying them is one entry. It does not store "player at position 342.5, 128.3, 0, rotation 45°, velocity 5.2, frame 12" as a single entry. It stores each of those values and operations individually.

And critically — the pool curates itself. Entries that are never hit again go dormant and eventually compress. The pool is not a ledger that grows with every unique moment. It is a living structure that grows toward the calculations that matter and shrinks away from ones that don't.

What the critique assumes
Store: {x:342.5, y:128.3, rot:45, vel:5.2, frame:12}
Store: {x:342.6, y:128.3, rot:45, vel:5.2, frame:12}
Store: {x:342.7, y:128.3, rot:45, vel:5.2, frame:12}
Trillions of combined states → 32GB instantly
What actually happens
Store: gravity = 9.81 [1 entry]
Store: velocity = 5.2 [1 entry]
Store: 9.81 × 5.2 = 50.412 [1 entry]
Position routes via digit trimming. Unique ops only.

Attack 4: The Halting Problem. Human input is unpredictable. The queue cannot know the future if the player presses the shield button 1ms before the hit.

The queue never predicts human input. It waits for it, then reads what follows with certainty.

This is the most important distinction in the entire system. The queue does not guess what the player will do. It does not predict button presses. Human input is genuinely unpredictable and the system makes no attempt to predict it.

What the queue does: the moment input arrives — the moment the player's button press enters the queue — the queue immediately reads the scripts that input will trigger and pre-loads their certain outcomes. The certainty begins after the input, never before.

What the critique thinks the queue does
Predict: player will not press shield
Pre-load: death animation
Player presses shield — WRONG
Pipeline flush — wasted work
What the queue actually does
Wait. Human input is unknown. Do not predict.
Player presses shield — input enters queue
Queue reads: shield equipped script triggers
Pre-load: block animation, parry window — certain.

The intentional delay exists precisely for this. When input arrives, the system has a brief window — microseconds — to read the triggered scripts and pre-load before execution catches up. The delay is not wasted time. It is the reaction window that makes post-input certainty possible.

If the player had NOT pressed shield: the enemy hit script triggers, queue reads it, death is certain, death is pre-loaded. If the player presses shield at the last millisecond: new input enters queue, queue discards the death pre-load, reads the shield script, pre-loads survival instead. The queue is fast enough that this switch costs almost nothing. Microseconds of re-routing versus milliseconds of execution time.

The queue does not predict humans. It reads code. Humans are unpredictable. Code, once triggered by human input, is not. That is the boundary. Everything before the button press is unknown. Everything after it is certain. The queue lives on the certain side of that line.
